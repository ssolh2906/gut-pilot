# G3 — Sample independence

> This decides the test family. Getting it wrong invalidates every p-value on the run, so it is
> confirmed even when the check is clean.

The only gate that is confirmed **even when nothing is wrong**. That is deliberate: the count table
physically cannot show pairing, so a clean check is not evidence of independence.

---

## 1. Anchor

`#gatePairing` · Design page · `renderPairing()`

Sub-elements: `#pairNote`, `#pairOpts` (two options), `#pairConf`.

## 2. Layer

| Field | Layer | Note |
|---|---|---|
| `checks.*` | Compute | ID uniqueness, column presence |
| `confidence` | Reasoning | 96% in the mock, a literal — §10 |
| `message`, `test_family` | Evidence (T6) | Design → test mapping is a table |

## 3. Endpoint

`GET  /api/session/{sid}/design/pairing`
`POST /api/session/{sid}/design/pairing` — `{ "design": "independent" | "paired" }`

## 4. Request

Depends on: **G1** (needs the sample roster). Independent of G2.

## 5. Response

```json
{
  "gate_id": "G3",
  "design": "independent",
  "checks": {
    "sample_ids": 24,
    "distinct_subjects": 24,
    "repeated_ids": [],
    "subject_id_column": false,
    "timepoint_column": false
  },
  "confidence": 0.96,
  "confidence_basis": "no_repeated_ids_and_no_timepoint_column",
  "message": "I checked for repeated subject identifiers and found none: 24 IDs, 24 distinct subjects, no timepoint column. ...",
  "options": [
    { "option_id": "independent", "label": "Independent samples",
      "test_family": { "alpha": "wilcoxon_rank_sum", "beta_permutation": "unrestricted" },
      "available": true, "default": true },
    { "option_id": "paired", "label": "Paired or repeated measures",
      "test_family": { "alpha": "wilcoxon_signed_rank", "beta_permutation": "within_subject" },
      "available": false,
      "unavailable_reason": "No subject_id column was supplied, so paired tests cannot be executed." }
  ]
}
```

`test_family` is on the option, not on the gate. The client shows the consequence *before* the
choice, which is the whole point of the sub-labels in the mock ("Wilcoxon rank-sum, unrestricted
permutations").

## 6. Invalidation

| Target | Effect |
|---|---|
| `alpha.tests` | rank-sum ↔ signed-rank |
| `beta.permanova` | permutation scheme: unrestricted ↔ within-subject strata |
| `da.*` | Wilcoxon is one of the three consensus methods (G10/DA), so its family changes too |

Medium cost — statistics recompute, but rarefaction and distances do not.

## 7. Evidence

| Table | Supplies | Status |
|---|---|---|
| **T6** Test-family selection | design → alpha test, beta permutation scheme, assumptions, source | Not built |

Minimum content:

| Design | Alpha test | Beta permutation | Requires |
|---|---|---|---|
| independent | Wilcoxon rank-sum | unrestricted | — |
| paired | Wilcoxon signed-rank | restricted within subject | `subject_id`, balanced pairs |
| repeated measures (>2) | Friedman, or mixed model | restricted within subject | `subject_id`, `timepoint` |

The mock offers only the first two. The third is listed because "paired or repeated measures" is one
button in the mock and they are not the same test.

## 8. States

| Condition | Behaviour |
|---|---|
| No `subject_id` column | `paired` is `available: false` with a reason. **The mock lets you select it and then admits a real run would need the column** — that is a mock affordance, not a spec |
| `repeated_ids` non-empty | Do **not** default to `independent`. Propose `paired` and name the repeats |
| G1 = single-cohort | Gate still applies to descriptive panels; group tests are off anyway |

**R7 — block, do not warn.** If `design = paired` and the data cannot support it (no `subject_id`,
or unbalanced pairs), the run does not proceed. This is the one rule in the system that blocks
rather than caveats: an unpaired test reported as paired is not a caveat, it is a wrong number.

```json
{ "error": "R7_PAIRED_UNSUPPORTED",
  "message": "Paired design was declared but no subject_id column was supplied. Supply one, or declare the samples independent.",
  "blocking": true }
```

## 9. Decision log

Recorded on **Confirm design and continue**, keyed `g3`.

```json
{ "gate_id": "G3", "page": "design", "actor": "human",
  "decision": "Samples declared independent, so tests use Wilcoxon rank-sum.",
  "confidence": null, "source": "human-in-the-loop" }
```

Logged **even when unchanged from the proposal.** This gate's value is the recorded confirmation;
an unlogged default would defeat it.

## 10. Open

1. The 96% is a literal. Proposed basis: 1.0 when a `subject_id` column exists and is unique,
   ~0.95 when inferred from ID uniqueness alone (absence of evidence, not evidence of absence).
   Needs a decision.
2. Split "paired" and "repeated measures" into two options, or keep one button? They map to
   different tests.
3. Where is `subject_id` uploaded? The metadata contract mentions it but no gate collects it, and
   G1's `assignment` does not carry it.
4. Does the DA consensus (ALDEx2, ANCOM-BC, Wilcoxon) have a paired form for all three methods? If
   not, `paired` may need to restrict the method set — unresolved.

## Deviations from the mock

- Mock allows selecting `paired` and explains afterwards that a real run needs `subject_id`. Spec
  disables the option and states the reason up front (§8).
- Mock's R7 is listed in the flow spec but not implemented; nothing blocks. Spec makes it a hard
  error response.
